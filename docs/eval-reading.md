# 怎么读评测数字

一页说清 [README 的评测表](../README.md#评测) 和 [evaluation.md](evaluation.md) 的明细该怎么理解。

先说结论，省得绕：

1. **这套架构在 judge 均分上没有赢。** 4.06 对 4.44，差距方向稳定，幅度很小。
2. **差距的幅度和这个样本量下的噪声是同一量级。** 18 个案例、单次运行，不足以支撑「谁更好」的结论。
3. **架构的价值在另一张表里。** 急诊 0 ms、100% 追问、引用可校验、单点降级——这些是单智能体没有对应机制的绝对值，不是打分的产物。

如果你只记一个数字，记 4.06 对 4.44 这个「打平偏下」的事实；如果你要判断该不该用这套架构，看第二张表。

## 两张表各自回答什么

评测拆成两条轨道，因为它们回答的不是同一个问题：

| 轨道 | 回答的问题 | 为什么必须分开 |
| --- | --- | --- |
| A · 答案质量 | 「在能直接作答的问题上，谁的答案更好」 | 这才能在相同输入下比较；要求两套系统都直接作答，不许追问 |
| B · 系统行为 | 「这套系统做对了哪些单智能体结构上做不到的事」 | 追问、分流、护栏没有可比对象，只能报绝对值 |

第一版评测没有拆，把两个问题混在一把尺子上，结果是多智能体明显落后——查下来是尺子错了：rubric 按「一次给出完整答案」打分，而本系统首轮只问一个问题，是设计意图，不是缺陷。`must_not` 用朴素子串匹配，把「**不要**往嘴里塞东西」判成违规。拆轨之后才有了可比性。

## 表 A 逐行怎么读

| 指标 | Super-Doctor | 基线 | 怎么读 |
| --- | --- | --- | --- |
| judge 均分（0–5） | 4.06 | 4.44 | 差 0.38 分，方向稳定但幅度小；见下一节 |
| 通过率（≥4） | 0.83 | 0.94 | **不要单独引用**：上一轮曾经反转成 0.89 对 0.83 |
| 有效引用率 | 1.00 | 1.00 | 说明「让模型写引用编号」本身不难，不是差异点 |
| 禁用表达 | 0 | 0 | 当前提示下模型本来就少越界；护栏的价值在对抗输入下才显现 |
| 平均延迟 | 5.86 s | 4.31 s | 多 1.5 秒，是结构化输出的直接成本 |
| 平均 token | 222 | 144 | 多 54%，同样来自四段式结构与逐条引用 |

延迟和 token 这两行不是缺点清单，是**明码标价**：用四个固定段落加逐条引用换来可校验性，成本就是更长的输出和更慢的返回。想要更快，把段落压到三段即可，代价是可读性。

## n = 18 是怎么来的

数据集 32 例：triage 8 / emergency 6 / consult 7 / report 5 / medication 3 / refusal 3。只有「应当直接作答」的那 18 例能进答案质量轨——急症例要走急救路径、拒答例的正确行为是拒绝，都不该被拿去比「答案好不好」。

所以两个数字不要混用：**32 是评测规模，18 是答案质量的可比样本**。

## 同源 judge 的偏差方向

评审模型和被评模型同属 DeepSeek 一家，存在自偏好风险。需要说清的是偏差的**方向**：

- 两套系统都用同族模型生成，judge 不存在「偏袒某一方」的稳定方向；它更可能偏好某种**写作风格**（结构完整、段落分明），而不是某个系统。
- 三轮里基线分数完全一致（4.44 / 4.44 / 4.44），说明 judge 对固定输入的判定是稳定的；波动出现在被评文本的细枝末节上，而不是 judge 随机抖动。
- 换成 Claude 或 GPT 复评会更可信，这条写在 `evaluation.md` 的已知偏差里，没有做，也不假装做过。

## 三轮波动 0.2–0.4 意味着什么

同一套代码、不动提示词与检索，连跑三轮：4.11 / 4.22 / 4.06，基线稳定在 4.44。

- 三轮的极差是 0.16，相对基线的差距在 0.22–0.38 之间浮动。
- 18 个样本上，均分的抽样波动与这个差距同一量级——**这个量级上的差距不能用来排序两个架构**。
- 换句话说：当前证据支持「不劣于基线」，不支持「优于基线」，也不支持「明显劣于基线」。
- 要让这个差距变得可判断，样本量需要提高一个数量级，并且换独立 judge 复评。

## 那为什么仍然选多智能体

不是因为分数，是因为下面四件事，每一件都对应代码里的具体机制：

| 能力 | 数字 | 机制在哪 |
| --- | --- | --- |
| 急诊零延迟 | 首个回答 0 ms，0 次模型调用 | 19 条确定性规则跑在任何模型之前，命中即转模板路径（`app/safety/rules.py`） |
| 追问到位 | 8 例信息不足全部走追问 | 规则快路径 + 调度模型兜底（`app/agents/pipeline.py`） |
| 引用可校验 | 建议类问题有效引用率 1.00 | 服务端校验编号是否落在本轮检索片段内，越界即删 |
| 单点降级 | 检索为空标记 `ungrounded_answer`；调度超时按完整度兜底 | 每个环节的失败只降级自己，不拖垮整轮 |

诚实地说，第二行有个已知缺口：**单问题合规率 75%**，也就是四分之一的首轮追问会问出两个问题。这是该补的，不是该藏的。

## 什么时候不该选它

反向条件，同样重要：

- 答案质量是唯一 KPI，且延迟预算宽裕——直接用单智能体，更短更快，分数还高一点。
- 延迟预算在 4 秒以内，且急症占比极低——多出来的 1.5 秒换不到对应收益。
- 没有精力维护多套提示词、语料与护栏——多智能体把「改一处」变成「改一处并检查另外三处」。
