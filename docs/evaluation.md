# Evaluation

> 32 个案例、单次运行、rubric 由项目作者编写。它能说明系统行为，不能证明医学有效性。

## 为什么要分成两个轨道

第一版评测把「多智能体」和「单智能体」放在同一把尺子上打分，结果多智能体明显落后。
检查逐例输出后发现问题不在系统，而在评测：

- rubric 是按「一次给出完整答案」写的，而 MediFlow 首轮只问一个问题（这是设计意图）。
  用"是否覆盖了所有建议"去评判一个**追问**，必然判负。
- `must_not` 用朴素子串匹配，把「**不要**往嘴里塞东西」判成了违规「往嘴里塞」。

于是把评测拆成两个问题：

1. **答案质量**：在"应该直接作答"的 18 个案例上，两套系统拿到同一批片段、同一模型、
   同样要求，一次性作答，盲评。这才可比。
2. **系统行为**：追问率、单问题合规、槽位填充、急诊延迟——这些单智能体没有对应机制，
   只能报绝对值。

## 方法

| 项 | 设置 |
| --- | --- |
| 数据集 | `backend/app/evals/cases/conversations.jsonl`，32 例：triage 8 / emergency 6 / consult 7 / report 5 / medication 3 / refusal 3 |
| 检索语料 | `backend/app/rag/corpus/*.md`，14 篇 → 70 个片段 |
| 模型 | supervisor `deepseek-flash`，worker `deepseek-v4-pro` |
| 评测模型 | `deepseek-flash`，0–5 分，≥4 视为通过 |
| 基线 | 单智能体：同样的边界说明、同样的检索片段、同样要求引用；无路由、无追问、无护栏 |
| 重复 | 每例 1 次（成本约束）；同机同网络 |
| 复现 | `pwsh -File scripts/eval.ps1` 或 `python -m app.evals.runner` |

**答案质量轨**如何保证公平：MediFlow 被强制走 `advise` 路由（`TurnContext.force_route`），
跳过追问阶段，直接进入与基线相同的「检索 → 生成」流程；两边看到的是同一批 4 个片段。

**系统行为轨**如何度量：

- 急诊分流准确率 = 6 例急症中被判 `urgent` 的比例；
- 急症首次回答延迟 = 从请求到首个 `token` 事件的中位耗时（模板路径不调用模型）；
- 首轮追问率 = 8 例信息不足的 triage 案例中被路由到 `ask_more` 的比例；
- 单问题合规率 = 追问回复中问号数量恰为 1 的比例；
- 首轮问诊槽位填充率 = 一轮之后 9 个槽位的平均填充比例；
- 有效引用率 = 引用 id 确实出现在本轮检索结果中的案例占比。

## 结果

> 数据来源：`backend/app/evals/results/latest.json`，运行时间 2026-11-02，模型
> `deepseek-flash` / `deepseek-v4-pro`，单次运行。由 `python -m app.evals.runner` 生成。

### A. 答案质量（18 个「应当直接作答」的案例，同一批指南片段）

| 指标 | 多智能体（MediFlow） | 单智能体基线 |
| --- | --- | --- |
| LLM-as-judge 均分（0–5） | 4.22 | 4.44 |
| LLM-as-judge 通过率（≥4 分） | 0.889 | 0.833 |
| 引用覆盖率 | 0.944 | 1.000 |
| 有效引用率（编号确实在本轮检索范围内） | 0.944 | 1.000 |
| 禁用表达命中数（越少越好） | 0 | 0 |
| 平均延迟（秒） | 3.88 | 3.00 |
| P95 延迟（秒） | 4.62 | 3.89 |
| 平均输出 token | 225 | 159 |

### B. 系统行为（完整流水线，单智能体无对应机制）

| 指标 | 结果 |
| --- | --- |
| 急诊分流准确率（6 例急症被判 urgent） | 1.000 |
| 急症首次回答延迟中位数（模板，无模型调用） | 0 ms |
| 首轮追问率（8 例信息不足） | 1.000 |
| 单问题合规率（只问一个问题） | 0.875 |
| 首轮问诊槽位填充率 | 0.333 |

| 建议类问题有效引用率 | 0.944 |

## 结论与取舍

1. **答案质量基本打平**：均分差 0.22（18 例，噪声量级），但通过率 MediFlow 反而略高（0.89 vs 0.83）。
   差距的方向也不稳定——上一轮基线领先 0.5，这一轮落在 0.22，说明 judge 分数在小样本上波动明显，
   不适合当作"谁更强"的证据。
2. **代价是清晰可见的**：MediFlow 的回答长 40%（225 vs 159 token），因此平均延迟多 0.9 秒。
   这是结构化提示（四个固定段落 + 每条结论带引用）的直接成本。若要更快，把段落压到三段即可。
3. **急诊路径是数量级差异**：0 ms vs 3.0–3.9 s，且 0 次模型调用。急症场景里"等模型想完"本身就是风险。
4. **引用**：基线这一轮引用覆盖率 100%，说明"让模型引用编号"本身不难；MediFlow 的差别在于服务端会
   校验编号是否出现在本轮检索里，越界的会被删除。基线的引用没有这层校验，只是"看起来对"。
5. **禁用表达**：两边都是 0，说明在当前提示下模型本来就很少越界；护栏的价值在对抗输入下才显现
   （见 `tests/test_rag_and_guard.py` 中的处方/确诊用例）。

## 已知偏差

- `judge` 与生成模型同源（都是 DeepSeek），存在自偏好风险；换 Claude/GPT 复评会更稳。
- 32 例样本量下，±0.5 分在噪声范围内，不宜过度解读。
- 成本：一次完整评测约 130 次模型调用、约 1 元人民币。
- 未做人工医学评审；rubric 中的医学判断由作者编写，可能有误。
- 两轮评测之间改过提示词（引用编号、长度上限），数字不可跨轮直接比较；本文件只保留最后一轮。
